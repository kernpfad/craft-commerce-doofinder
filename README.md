# Commerce Doofinder

A Doofinder integration for Craft Commerce: real-time product/variant sync to a Doofinder search index, plus a zero-downtime full-catalog reindex command. Doofinder's own drop-in "Layer" search widget handles the front end entirely — this plugin's whole job is keeping the index in sync, never inline in a customer-facing request.

## Why this exists

No Craft CMS/Commerce integration for [Doofinder](https://www.doofinder.com) exists — confirmed by direct slug checks against the Craft Plugin Store (no fake-positive risk this time; see [`../IDEAS.md`](../IDEAS.md) for the methodology and why that check matters here) and a Packagist search that only turns up official Doofinder modules for other platforms (Magento 2, Pimcore, Thelia). Doofinder's own support docs tell merchants on an unsupported CMS to contact support directly.

## Requirements

- Craft CMS 5.0.0+
- Craft Commerce 5.0.0+
- PHP 8.2+
- A Doofinder account: an API token and a search engine hash ID (both from the Doofinder Admin Panel)

## What it does

- **Real-time sync on variant save/delete**: saving a product's variant pushes its Doofinder item (grouped under the parent product via `group_id`/`group_leader`, Doofinder's own documented convention for product variants) to the configured index. Deleting a variant, or the whole product, removes the corresponding item(s). Every Doofinder API call runs on the queue — a Doofinder outage never blocks a product save.
- **Zero-downtime full reindex**: `php craft doofinder/reindex` builds a complete, fresh index in a locked temporary index (Doofinder's own documented workflow — verified against `docs.doofinder.com`, not guessed), pushes the whole catalog into it in chunks of 100 items (Doofinder's documented bulk-request limit), then atomically swaps it in for the live index. Search traffic keeps hitting the still-live, still-complete old index for the entire duration of the run.
- **Custom field mapping**: map any Craft product field handle to any Doofinder item custom field via a plain `handle=key` list in settings (Doofinder items accept arbitrary extra keys beyond their reserved ones). Read from the product, applied to every variant of that product.
- **Configurable queue component**: same pattern as [Commerce Klaviyo](../commerce-klaviyo) — route this plugin's sync jobs to a different Yii application component (a real message-queue backend configured in `config/app.php`) instead of Craft's default queue. Falls back to the default queue, logged rather than thrown, if the configured component isn't available.
- **No front-end work required.** Doofinder ships "Layer," a single drop-in `<script>` tag configured entirely from the Doofinder Admin Panel (search box detection, results popup, facets, analytics). This plugin doesn't need to (and doesn't) build any search-results UI — paste Doofinder's own installation script into your layout and it's live.

## What it doesn't do (yet)

- **No automatic `image_link`.** Like [Commerce Klaviyo](../commerce-klaviyo)'s `image_full_url`, product images are always a project-specific custom field in Commerce's schema — this plugin can't read one without guessing at a project's setup. Map an asset field's URL through the custom field mapping if you need it populated.
- **No categories.** Doofinder's `categories` field (hierarchical `"Parent > Child > Leaf"` strings) isn't populated automatically in v1 — Commerce doesn't have a single universal category concept the way some other platforms do (a store's actual category structure is usually a category group, a Matrix field, or plain product-type segmentation, and isn't safe to guess). Map it through the custom field mapping if your project has a suitable field.
- **No availability/stock field.** Not part of Doofinder's documented reserved-field set; map it via a custom field if your Doofinder facet configuration needs it.

## Design notes

- **The API client sets explicit request timeouts** (5s connect, 15s total; 60s for the bulk endpoint, which accepts up to 100 items and is only called from the reindex command). `Craft::createGuzzleClient()` configures only a User-Agent and an optional proxy (verified against Craft's source), so without them the client inherits Guzzle's default of *no timeout at all* — an unresponsive Doofinder would have held a queue worker open until PHP's execution limit rather than failing and letting Craft retry the job.
- **Drafts, revisions, and propagation saves are never indexed.** Craft fires `EVENT_AFTER_SAVE`/`EVENT_AFTER_DELETE` for drafts and revisions too, and each is a *separate element with its own ID* — verified against real saves, not assumed. Since this plugin uses the Craft element ID as Doofinder's item `id`, indexing them put entries in the merchant's **live search index** that no customer can ever buy. The revision case was the damaging one: Craft creates a revision on every CP publish, so an actively-edited store accumulated one junk indexed item per edit, permanently (nothing removes them — deletion only fires for real products), each appearing in real customer search results. Multi-site propagation saves are skipped for a related but milder reason: on a two-site install one product save fired the listener twice per element, doubling the API calls for byte-identical data. All three are now filtered by a single `CatalogSyncService::isSyncable()` guard, covered by regression tests.
- **Deleting a whole product queues some redundant delete calls, deliberately.** Each variant fires its own `EVENT_AFTER_DELETE` *and* the product-level handler enumerates the product's variants, so a product delete issues a couple of duplicate deletes. That's kept on purpose: `DoofinderClient::deleteItem()` treats a 404 as success, so duplicates are harmless, whereas dropping the product-level handler to save the calls would risk leaving orphaned index entries in any path where per-variant events don't fire. Redundant network calls on an infrequent operation are the cheaper side of that trade.
- **Syncs on `Variant::EVENT_AFTER_SAVE`, not `Product::EVENT_AFTER_SAVE`** — verified against a real save, not assumed: at the exact moment a Product's own `EVENT_AFTER_SAVE` fires, its variants haven't been persisted yet (`$variant->id` is still `null`, and a fresh database query for them returns nothing), because Commerce saves a product's variants as their own, later element saves. Listening at the product level would silently skip every variant on every real save — which is exactly what happened in this plugin's own first draft, caught by an integration test failure and traced with a debug listener rather than assumed to be "probably fine." Commerce Klaviyo had this same gap for the same reason; finding it here is what surfaced it there, and it has since been fixed the same way.
- **Deliberately not built on the official `doofinder/doofinder` Composer package**, despite it being a plausible first choice (and despite this plugin's own planning notes in `../IDEAS.md` originally assuming it'd be usable). Its GitHub README (the `master` branch) describes a `ManagementClient` with a temporary-index/reindex workflow that doesn't exist in the actual, currently-installable v5.x release — inspecting the real installed source found `Doofinder\Api\Management\Client`, a raw-`curl_init()` client targeting Doofinder's old `/v1` API (no temporary-index concept at all), not the current, documented `/api/v2` surface this plugin needs. Built a direct Guzzle-based `DoofinderClient` against the real `/api/v2` REST API instead — the same choice already made for Klaviyo's SDK, for an unrelated reason (typed objects there vs. a version mismatch here), but the same conclusion: send the documented JSON directly.
- **Two specifics are genuinely undocumented in Doofinder's own current API reference**, implemented as the most REST-convention-consistent assumption rather than guessed silently: (1) how bulk item writes reach a temporary index once one exists — read as the *same* item-write endpoints getting transparently routed to the temporary copy while its lock is active, since no distinct temp-specific item-write path is documented anywhere; (2) the temporary-index delete/cancel endpoint's exact path — inferred as `DELETE .../indices/{name}/temp/`, the direct REST counterpart of the documented `POST .../indices/{name}/temp/` create call. See `DoofinderClient`'s class docblock.
- **Doofinder's behavior on creating an item with an already-existing ID is also undocumented.** `DoofinderClient::upsertItem()` defensively tries a create first and falls back to a PATCH update on a 409 response — the same pattern already proven for Klaviyo's catalog upsert — pending confirmation against a real Doofinder trial account (see "Testing status").
- `Product::getPromotionalPrice()` (verified against the installed Commerce 5 source) returns `null` when nothing's on sale and a lower price only when a real discount applies — the correct source for Doofinder's optional `sale_price` field, as opposed to `getSalePrice()`, which always returns a value (falling back to the regular price) and would need extra filtering to avoid setting `sale_price` equal to `price` on every item.

## Testing status

- **Unit tests** (`tests/unit`): `ItemPayloadBuilderTest` verifies the item payload shape (including the sale-price-only-when-actually-lower logic) against Doofinder's documented reserved fields; `FieldMapperTest` covers the custom field mapping logic (same pattern as Commerce Klaviyo's `ProfileMapper`); `SettingsTest` covers zone/index defaults and the derived API host; `DoofinderClientTest` exercises the upsert-falls-back-to-update-on-409 and delete-tolerates-404 logic against a Guzzle `MockHandler`, without a real network call — the same injectable-client pattern already used for `KlaviyoClient`.
- **Integration tests** (`tests/integration`): boot a real Craft + Commerce application and drive the actual production event-listener pipeline with real products and variants. Rather than executing queued jobs against the real Doofinder API (no credentials exist in this environment), these tests inspect Craft's own queue to confirm the right jobs were queued: saving a product (which saves its variant) → sync job; product delete → delete job; plus direct verification that `CatalogSyncService::buildVariantPayloads()` produces the correct `group_id`/`group_leader`/price shape from a real Product/Variant, and the same `getSyncQueue()` default/fallback coverage already proven for Commerce Klaviyo. The variant-vs-product event-timing issue above was caught by this suite (the sync-job test failed against the original `Product::EVENT_AFTER_SAVE`-based implementation) — not found by inspection. Two further tests are the regression coverage for the draft/revision bug described in "Design notes": saving a draft and creating a revision must each queue *no* Doofinder job at all. 9 tests.
- **Not verified against a real Doofinder account** (no credentials exist in this environment): whether creating an item with a duplicate ID actually returns a 409 (the assumption `DoofinderClient::upsertItem()` is built on); the two undocumented-and-inferred specifics above (temp-index bulk-write routing, the temp-index delete endpoint's exact path); the exact partial-failure response shape of the `_bulk` endpoint; and the full `doofinder/reindex` console command hasn't been run end-to-end against a live search engine. Documented here rather than silently left unclear — same approach as the CleverReach plugin's own "not verified" section.
- Quality tooling (ECS with the `CRAFT_CMS_4` set, PHPStan at level 8 via `craftcms/phpstan`, Rector with the `CRAFT_CMS_50` set) all run clean.
